# 15 赶紧收藏！GPT-5.6 Sol 提示词指南+案例大全

本文根据 [OpenAI 官方 GPT-5.6 Sol 提示指南](https://developers.openai.com/api/docs/guides/prompt-guidance-gpt-5p6) 翻译并改写。

官方文档主要面向 API、Agent 和工具调用，但其中的提示原则也适合 Codex 用户。

::: info 说明
文中的中文案例是按官方原则改写的 Codex 场景，不是 OpenAI 官方案例。模型能力、API 限制、价格和可用范围，请以官方模型文档为准。
:::

## 核心结论

这份指南的中心思想可以概括为：

> **不要靠堆叠大量过程指令来“控制”GPT-5.6。应该写清目标、边界、证据、验收标准和停止条件，再让模型自行选择高效路径。**

提示词的写法正在发生变化：

- 从“逐步规定模型怎么做”，转向“定义最终要达到什么状态”
- 从“越详细越稳”，转向“只保留真正改变行为的约束”
- 从“凭感觉调提示词”，转向“用代表性评测逐项验证”

这里的评测，也叫 eval。

简单理解，就是准备一批真实任务，每次修改提示词后都用同一批任务复测。

OpenAI 分享了一组内部编码 Agent 实验结果：更精简的系统提示词让评测分数提升约 10%～15%，总 Token 减少 41%～66%，成本减少 33%～67%。

这些只是方向性数据，不能直接套用到所有项目，必须用自己的任务验证。

## 一、最重要的原则：Outcome-first

Outcome-first，就是先写“终点”，不要先编排“路线”。

不太理想的写法是：

```text
先搜索政策。
然后检查客户账户。
然后判断是否符合条件。
如果不符合，再搜索一次。
最后生成回复。
```

更符合官方指南的写法是：

```text
目标：端到端解决客户的问题。

成功标准：
- 根据现有政策和账户证据完成资格判断
- 在权限允许时执行可执行操作
- 返回 completed_actions、customer_message 和 blockers
- 缺少必要证据时，只询问最小的缺失字段
```

第一种控制过程，第二种控制结果、边界和完成状态。

GPT-5.6 可以根据真实结果调整搜索、推理和工具路线，不会被过细或过时的流程束缚。

写复杂提示词时，优先回答五个问题：

1. 用户最终应该得到什么？
2. 什么条件满足后才算完成？
3. 哪些约束绝对不能违反？
4. 可以使用什么证据和工具？
5. 什么情况下应该停止、回退或询问？

::: tip Prompt
修复注册按钮没有反应的问题。完成标准：找到根因，完成最小修改，验证注册成功和失败状态，最后说明改动与验证结果。
:::

## 二、提示词简化不是单纯“缩短”

官方所说的简化，是提高指令密度，不是机械删字。

### 建议删除

- 同一规则的重复表达
- 不影响行为的风格要求
- 没有带来行为变化的示例
- 模型本来就能稳定执行的过程说明
- 与当前任务无关的工具及工具描述

### 必须保留

- 用户可见的最终结果
- 成功标准与停止条件
- 安全、业务、证据和权限限制
- 依赖上下文的工具路线
- 输出格式与验证要求

GPT-5 类模型会认真遵守提示契约。

互相冲突的规则，可能比少写一条规则更容易造成不稳定。

例如：

```text
永远不要猜测。
缺失信息时必须询问用户。
尽量不要询问用户。
请主动完成任务。
只使用明确提供的数据。
可以根据上下文推断合理默认值。
```

每句话单独看都合理，放在一起却没有优先级。

可以改成：

```text
优先使用明确提供的数据。

缺失值能根据上下文或既定 schema 唯一确定时，可以推断。
缺失值会实质影响结果且无法可靠确定时，只询问最小的必要信息。
```

这就是决策规则：先说明判断条件，再让模型根据实际情况选择。

## 三、把绝对规则留给真正的不变量

`always`、`never`、`must`、`only` 只适合真正不能破例的规则，例如：

- 安全边界
- 必填字段
- 法规或业务硬约束
- 永远不能发生的副作用
- 固定输出协议

下面这些问题通常不适合写成绝对规则：

- 什么时候搜索
- 什么时候追问
- 什么时候调用工具
- 是否继续尝试
- 回答应该多长
- 是否需要更多证据

应该写成：

```text
缺少关键事实、日期、负责人、ID 或引用时，再执行一次检索。
```

不要写成：

```text
回答前必须搜索三次。
```

前者控制质量，后者只控制次数。

## 四、停止条件是高质量 Agent 提示词的核心

很多提示词只写“做什么”，没有写“何时停止”。

模型每次拿到工具结果后，都应该判断：

- 当前证据是否足以回答核心请求？
- 是否仍缺少必要事实？
- 下一步最小有效动作是什么？
- 是否已经进入没有收益的循环？

官方建议使用尽量少但有价值的工具循环。

但不能为了少调用工具，牺牲正确性、证据、计算和引用。

::: tip Prompt
每次获得结果后，判断证据是否足够。足够就回答；仍缺关键事实时，只做一次最小有效补查。不要为了润色措辞或增加次要例子继续搜索。
:::

停止规则可以防止：

- 无限搜索
- 重复调用同一工具
- 不断扩大任务范围
- 明明能回答却迟迟不输出
- 为追求最少调用而过早结束

## 五、人格与协作方式要分开

Personality 控制表达方式：

- 语气和温度
- 正式与直接程度
- 幽默和同理心
- 文本润色程度

Collaboration style 控制做事方式：

- 什么时候提问
- 什么时候合理假设
- 是否主动推进
- 是否解释取舍
- 如何检查工作
- 如何处理不确定性

两部分都要短，而且不能代替目标、成功标准、工具规则和停止条件。

```text
Personality：
直接、沉稳、专业。避免泛泛的赞美和不必要的结束语。

Collaboration：
信息足够时主动完成任务。
只有缺失信息会实质改变结果且无法可靠推断时，才询问用户。
发现重要不确定性时，说明问题并给出下一步。
```

“友好”“有帮助”这类词过于模糊。

写清具体行为，模型才知道应该怎样表达和协作。

## 六、不要用“简洁”牺牲任务完整性

GPT-5.6 默认比 GPT-5.5 更简洁。

迁移旧提示词时，`Be concise`、`Keep it short` 可能已经多余，甚至会让答案过短。

API 用户可以用 `text.verbosity` 设置整体详细程度：

- `low`：简短
- `medium`：适中
- `high`：详细

提示词再补充本次任务必须保留的内容。

::: tip Prompt
先给结论，保留必要证据、重要限制和下一步。优先删除重复内容、泛泛安慰、次要背景和不必要的开场。
:::

这比“简短回答”更可靠，因为它写清了压缩信息的顺序。

## 七、自治权限必须分层定义

GPT-5.6 可以持续执行多步骤任务，但提示词必须写清：

- 哪些动作可以自动执行
- 哪些动作只能检查或建议
- 哪些动作必须获得批准

官方给出的边界可以整理为：

| 权限层级 | 适合的行为 |
| --- | --- |
| 自动执行 | 读取文件、检查日志等只读操作 |
| 执行后报告 | 范围内的本地修改和非破坏性验证 |
| 执行前确认 | 外部写入、破坏性操作、付费、公开发布或扩大范围 |

回答、解释、审查、诊断或规划类请求，默认检查材料并报告结果，不主动修改。

修改、构建或修复类请求，可以完成范围内的本地修改，并运行非破坏性验证。

如果反复写“先问我”“不得修改”“等待批准”，模型可能连正常的读取和测试也频繁请求确认。

::: tip Prompt
检查登录报错并修复相关代码，可以读取文件、查看日志和运行测试。删除数据、修改线上环境或扩大修改范围前，先征得我的确认。
:::

## 八、工具描述应该像接口合同

工具描述至少要说清：

- 工具能做什么
- 什么情况使用
- 关键返回内容是什么
- 失败或空结果时怎么办

只保留当前任务真正相关的工具。

无关工具会增加选择难度和 Token 消耗。

工具之间还要写清依赖关系：

- 独立读取可以并行
- 后一步依赖前一步结果时要串行
- 并行读取后，先综合结果再执行动作
- 结果为空、残缺或异常少时，尝试一两个有意义的替代办法

```text
执行账户操作前，先完成身份、资格和政策检索。
政策与账户读取互不依赖，可以并行。
账户操作依赖资格判断，必须在综合证据后执行。
```

不要因为结果看起来明显，就跳过必要的前置检查。

## 九、Programmatic Tool Calling 不是“工具多就用”

Programmatic Tool Calling，简称 PTC。

它是偏 API 和 Agent 开发的进阶能力。

普通 Codex 用户只要理解它的选择原则，不必强行使用。

PTC 适合边界明确、可以用代码压缩中间结果的任务，例如：

- 过滤、连接、排序、排名、去重和聚合
- 批量处理大量同类记录
- 重复执行确定性校验
- 把大型结构化结果压缩成小型 schema

下面这些情况更适合直接调用工具：

- 一次调用就能完成
- 中间结果很小
- 每一步都会改变下一步判断
- 操作需要审批
- 最终回答必须保留原始引用或文件
- 工具之间需要语义判断

判断标准不是“工具多不多”，而是中间阶段能否被限定为确定性的记录处理。

使用 PTC 时还要写明处理阶段、可用工具、输出格式、重试次数、停止条件，以及何时交还给模型判断。

`program_output` 和最终回答是两份输出，都要测试。

程序可能返回正确记录，但最终回答仍可能漏掉字段、引用或限制。

## 十、检索与引用需要“预算”

普通问答可以这样控制检索：

1. 先用简短、有区分度的关键词搜索一次。
2. 结果足以支持核心回答时停止。
3. 缺少关键事实、日期、负责人、ID、来源或指定文档时再搜索。
4. 不要只为改善措辞或增加次要例子继续搜索。

研究和综合任务还要明确：

- 只引用实际读取过的来源
- 引用紧跟它所支持的结论
- 推断与已证实事实分开
- 说明来源之间的冲突
- 证据不足时缩小结论，不要猜

没有找到证据，不等于事实不存在。

合理的回答是“当前证据不足以确认”，而不是直接说“没有”。

::: tip Prompt
查清这个功能是否已经发布。只引用实际读取的官方来源；没有找到明确证据时，回答“暂时无法确认”，不要推断为“尚未发布”。
:::

## 十一、长任务只需要少量进度更新

工具密集型任务开始前，可以用一两句话说明第一步。

之后只在两种情况下更新：

- 进入新的重要阶段
- 新发现改变了原计划

每次更新只写一个具体结果和下一步。

不要逐项播报“正在搜索”“正在打开文件”“正在运行命令”。

这样既能让用户知道任务没有卡住，也不会被流水账打扰。

如果通过 API 手动回放历史消息，还要保留 assistant 原有的阶段值，避免把过程更新误当成最终答案。

## 十二、不要先提高 reasoning effort

迁移到 GPT-5.6 时，先保持 GPT-5.5 或 GPT-5.4 原来的推理强度作为基线。

然后测试同一档和低一档：

- `low`：重视速度，而且测试证明质量不下降
- `medium`：平衡型起点
- `high` 或 `xhigh`：评测证明有明显收益时再用
- `max`：只留给最难、质量优先的任务，不要全局开启

提高推理强度前，先检查提示词是否缺少：

- 成功标准
- 依赖规则
- 工具路线
- 验证闭环

很多看似“模型想得不够”的问题，其实是任务合同没有写清。

## 十三、验证必须进入成功标准

验证不是可有可无的最后一步，而是完成定义的一部分。

代码任务应根据项目情况运行：

- 针对本次行为的测试
- 类型检查或 lint
- 受影响包的构建
- 完整验证成本过高时的最小冒烟测试

无法运行验证时，要说明原因和次优检查办法。

视觉任务必须先渲染，再检查：

- 布局与裁切
- 间距和对齐
- 缺失内容
- 视觉一致性
- 响应式与必要状态

实施方案则要覆盖需求、文件或资源、状态变化、数据流、验证、失败处理、安全隐私，以及真正影响实施的问题。

::: tip Prompt
调整首页卡片间距，沿用现有设计规范。修改后渲染桌面端和移动端页面，检查对齐、溢出和响应式；无法检查的项目要明确说明。
:::

“完成”不只是生成答案，而是生成、验证，并如实报告无法验证的部分。

## 推荐提示词结构

官方给出的复杂提示词骨架是：

```text
Role:
[模型的职责与上下文]

Personality:
[语气与协作方式]

Goal:
[用户可见的结果]

Success criteria:
[最终回答前必须满足的条件]

Constraints:
[政策、安全、业务、证据和副作用限制]

Tools:
[使用哪些工具、何时使用、何时不使用]

Output:
[章节、长度、格式和语气]

Stop rules:
[何时重试、回退、拒绝、询问或停止]
```

关键不是把每一节写长，而是只保留真正会改变行为的信息。

## 一个更实用的中文模板

```text
角色
你是[职责]，服务于[项目或业务环境]。

目标
完成[用户可见的最终结果]，不要只提供中间分析。

成功标准
- [必须完成的判断或动作]
- [必须覆盖的关键信息]
- [必须使用的证据]
- [必须执行的验证]
- [最终输出必须包含的内容]

限制
- 不得违反[安全、合规或业务规则]
- 不得虚构事实、日期、指标或来源
- 外部写入、破坏性操作、付费或扩大范围前，先获得确认
- 范围内的读取、本地修改和非破坏性验证可以直接执行

工具
- 只使用当前任务需要的工具
- 必要的检索和验证是执行动作的前置条件
- 独立读取并行；存在依赖时串行
- 结果为空或异常少时，最多尝试两个有意义的替代办法

输出
- 先给结论
- 保留必要证据、重要限制和下一步
- 使用[指定格式]
- 删除重复、泛泛背景和不必要客套

停止规则
- 核心请求已有充分证据时停止检索并回答
- 缺少关键事实时，执行最小有效检索或询问
- 不为改善措辞或增加非必要细节继续调用工具
- 无法验证时说明原因，不得声称已经验证
```

## 5 个简短易懂的 Codex 案例

### 1. 修 Bug

::: tip Prompt
修复商品无法加入购物车的问题。找到有代码证据的根因，只改相关代码；修复后测试成功和失败情况，并说明改动。
:::

### 2. 只审查

::: tip Prompt
审查当前登录功能的改动，不要修改文件。只报告会导致错误、安全问题或测试缺失的具体问题，并写明文件和影响。
:::

### 3. 改页面

::: tip Prompt
让首页主按钮更醒目，沿用现有设计，不新增功能。完成后检查电脑和手机页面，确认没有溢出或错位。
:::

### 4. 查资料

::: tip Prompt
查清这个功能的官方用法。只引用实际读取的官方资料；证据足够就停止，无法确认的内容不要猜。
:::

### 5. 做长任务

::: tip Prompt
检查并修复站内失效链接。可以修改项目并运行构建；不要删除或重命名页面。只在扫描完成、开始修复和验证完成时汇报进度。
:::

## 对迁移工作的直接建议

不要把现有 GPT-5.5 提示词一次全部重写。

官方推荐的迁移顺序是：

1. 只切换模型，保持原来的 reasoning effort。
2. 先运行一批代表性评测。
3. 删除过时脚手架、重复规则和无关工具。
4. 只针对实际测出的退化，添加一条最小修复规则。
5. 每次只改一个变量，并重新运行同一批评测。

如果同时修改模型、提示词、工具和推理强度，就无法判断结果变化来自哪里。

出现退化时，选择少量真实任务记录，确认失败类型，做一次小修改，再运行相同任务。

## 总体评价

这份指南的价值，不是提供更多“提示词技巧”。

它把提示工程变成了 Agent 系统设计和实验工程。

可以用一个公式理解：

```text
高质量提示词
=
明确目标
+ 可验证的成功标准
+ 最小必要约束
+ 清晰权限边界
+ 与上下文有关的工具路线
+ 明确停止条件
+ 代表性评测
```

而不是：

```text
高质量提示词
=
更多规则
+ 更多示例
+ 更多强调
+ 更高推理强度
```

最值得先做的三件事：

1. 把过程指令改写成目标和验收标准。
2. 为工具型任务补上权限边界和停止条件。
3. 用逐项删减和评测，代替一次性重写提示词。
